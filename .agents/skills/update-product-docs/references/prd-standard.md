# PRD 품질 기준

제품 요구사항 문서(PRD)를 작성하거나 검토할 때 이 기준을 사용한다.

## PRD가 담당하는 내용

PRD에서는 제품 변경이 필요한 이유, 혜택을 받는 대상, 필요한 관찰 가능 동작, 범위에서 제외하는 내용, 성공 여부를 판단하는 방법을 설명한다.

PRD에서 다음을 담당하지 않는다.

- 정책에서 다뤄야 하는 정확한 권한 및 상태 전이 규칙
- 프로토콜, 저장소, 라이브러리, 스키마, 프레임워크 선택
- 작업 트리 지침과 파일 단위 구현 계획
- 제품 의도와 별개로 변경되는 프로젝트 일정

## 필수 내용

승인된 PRD만 읽고 다음 질문에 쉽게 답할 수 있어야 한다.

1. 현재 어떤 사용자 문제 또는 운영 문제를 해결하는가?
2. 어떤 근거나 관찰이 그 문제를 뒷받침하는가?
3. 누가 어떤 맥락에서 문제를 겪는가?
4. 사용자와 조직에 어떤 결과 변화가 필요한가?
5. 무엇을 명시적으로 범위에 포함하고 제외하는가?
6. 가장 짧은 대표 사용자 흐름은 무엇인가?
7. 제품이 어떤 관찰 가능한 동작을 제공해야 하는가?
8. 각 요구사항의 수용 또는 거부를 어떻게 판정하는가?
9. 어떤 정책 규칙이 동작을 제약하는가?
10. 어떤 의존성, 위험, 가정, 미결정 사항이 남아 있는가?
11. 어떤 기준선, 목표, 측정 기간, 데이터 출처로 성공을 정의하는가?

## 요구사항 품질

요구사항 하나에는 관찰 가능한 동작 하나만 작성한다.

좋은 예:

> `PRD-02-FR-03` — 사용자가 알림을 끄면 다음 운영일부터 11시 알림을 보내지 않는다.

나쁜 예:

> 알림 경험을 적절히 개선하고 설정도 제공한다.

각 요구사항에 다음을 포함한다.

- 행위자 또는 시작 조건을 식별한다.
- 관찰 가능한 결과를 명시한다.
- 승인된 제품 제약이 아니라면 구현 세부사항을 피한다.
- 하나 이상의 수용 기준으로 연결한다.
- 상태, 권한, 데이터, 실패 동작이 중요하면 영향을 받는 정책 규칙으로 연결한다.

승인된 PRD에는 모든 기능 요구사항을 하나 이상의 수용 기준과 정본 정책
규칙에 연결하는 추적성 매트릭스를 포함한다. `PRD-02-FR-03`,
`PRD-02-AC-04`, `POL-01-R-02`처럼 완전한 ID를 사용하고 `FR-03`이나
`AC-04`로 줄이지 않는다.

## 수용 기준 품질

경계 동작에는 짧은 전제/행동/결과 시나리오를 우선 사용한다. 관련 있는 경우 성공, 실패, 복구, 시간 경계, 권한, 동시성 사례를 포함한다.

수용 기준은 독립적으로 판정할 수 있어야 한다. `정상적으로 동작한다`, `빠르다`, `사용하기 쉽다` 같은 표현을 관찰 가능한 결과나 미결정 지표 항목으로 바꾼다.

## 지표

각 지표에 다음을 기록한다.

| 항목 | 의미 |
|---|---|
| 기준선 | 현재 관찰값 또는 `측정 필요` |
| 목표 | 원하는 값. 근거 없이 만들지 않는다 |
| 측정 기간 | 지표를 측정하는 기간 |
| 출처 | 이벤트, 설문, 관찰, 운영 기록 |
| 가드레일 | 지표를 최적화하는 동안 증가해서는 안 되는 피해 |

내부 도구에 인위적인 매출이나 MAU 목표를 둘 필요는 없다. 운영 시간, 누락률, 중복 조율, 성공적 완료, 자발적 반복 사용이 더 나은 신호일 수 있다.

## 문서 크기

첫 화면이 한 페이지 요약으로 유용하게 구성되도록 한다. 여러 기능에 걸친 정확한 규칙은 정책으로 옮겨 연결한다. 후속 기능에 독립적인 문제, 결과, 성공 지표, 생명주기, 출시 결정이 있다면 PRD를 분리한다.

분리한 문서들이 나눌 수 없는 하나의 전달 결정을 공유한다면, 단지 문서가 길다는 이유로 분리하지 않는다.
