# 제품 요구사항

`docs/prd/`는 제품 정의 과정에서 확정된 요구사항을 구현 가능한 제품 요구사항으로 정리하는 정본 영역입니다. 현재 PRD는 2026-07-24 제품 회의와 후속 정합성 검토의 D-29~D-45 결정을 포함합니다.

- `product-definition/`은 결정에 이른 배경과 논의 과정을 보존합니다.
- `prd/`는 제품이 제공해야 하는 기능, 범위와 수용 조건을 정의합니다.
- `policies/`는 상태 전이, 권한, 충돌, 보존과 예외 처리의 세부 규칙을 정의합니다.

PRD와 정책 문서가 충돌하면 제품 범위와 사용자 가치는 PRD를, 세부 동작은 정책 문서를 기준으로 판단합니다. 어느 쪽으로도 해소되지 않는 충돌은 임의 구현하지 않고 제품 결정을 추가합니다.

## 문서

| 문서 | 상태 | 역할 |
|------|------|------|
| [01. LunchTime MVP](./01_lunchtime_mvp.md) | `approved` / `planned` | 첫 MVP의 제품 범위, 사용자 경험, 기능 요구사항, 수용 조건과 D-29~D-45 결정 반영 |

## 변경 원칙

- 현재 MVP 문서는 첫 번째 PRD이며, 성공 기준 표의 기준선·목표·측정 기간·출처·가드레일은 파일럿 증거로 확정하고, 그 결과가 없는 미검증 지원 범위는 출시하지 않습니다.
- 독립적인 사용자 문제·성과·수용 기준과
  출시 결정을 가진 후속 범위는 `02_...`, `03_...`처럼 새 PRD로 추가합니다.
- 기존 PRD가 약속한 결과의 보완이나 오류 수정은 새 문서를 만들지 않고 해당
  PRD를 갱신합니다.
- 각 문서는 `PRD-NN`을 가지며 요구사항·수용 기준·기술 검증 ID는
  `PRD-NN-FR-NN`, `PRD-NN-AC-NN`, `PRD-NN-SP-NN` 형식을 사용합니다.
- 구현 작업은 관련 PRD 요구사항 ID와 정책 규칙을 연결합니다.
- PR을 올리기 전에 구현 결과가 PRD·정책 문서를 바꾸는지 확인합니다.
- 제품 동작이 달라졌다면 코드와 문서를 같은 PR에서 갱신합니다.
- 아직 기술 검증이 필요한 사항을 보장된 제품 동작처럼 표현하지 않습니다.
- 기술 스파이크는 확정된 사용자 결과를 바꾸지 않고 구현 방식, 수치 허용치와 실패 시 안전 차단(fail-closed) 사용자 경험만 구체화합니다. 각 기술 스파이크에는 책임자, 해소 시점과 출시 차단 조건을 기록합니다.
