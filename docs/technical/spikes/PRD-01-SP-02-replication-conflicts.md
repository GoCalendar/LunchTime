## 1. 이 문서의 상태

[PRD-01](../../prd/01_lunchtime_mvp.md) 9절이 이 스파이크에 묻는 질문은 "ACK, 늦은 전파, 취소, 메시지 순서와 중복 참여를 어떤 방식으로 결정적으로 수렴할 것인가"이고, 출시 차단 조건은 "메뉴 누락 방지와 충돌 수렴 시험 증거"입니다.

이번 범위에서 확인한 것과 확인하지 못한 것은 이렇습니다.

| 이슈 완료 조건 | 상태 |
|---|---|
| 순서와 중복이 다른 동일 이벤트 입력을 여러 Peer에 적용해 최종 projection이 일치 | **충족** — 4절 fixture 1·2, 순열 8·16회에서 세 Peer가 각각 hash 하나만 냈습니다 |
| 전송 성공과 정확한 리비전 저장 ACK가 구분되고 ACK 없는 참여·메뉴는 성공으로 판정되지 않음 | **충족** — 4절 fixture 4 |
| 같은 사용자의 분기 메뉴와 다중 Room 참여는 자동 승자 없이 확인 필요로 남음 | **충족** — 4절 fixture 6·7 |
| 마감 전 승인됐으나 늦게 도착한 참여와 마감까지 ACK가 없던 참여가 서로 다른 결과 | **충족** — 4절 fixture 5 |
| 모델 한계와 구현에 필요한 불변식 명시 | 아래 5절·6절 |

**그러나 이것으로 `PRD-01-SP-02`의 출시 차단 조건이 풀리지는 않습니다.** 확인한 것은 **논리 프로토콜의 수렴·차단 계약**이며, 그 계약이 실제 앱에서 성립하려면 아직 결정되지 않은 네 가지가 필요합니다.

- wire schema·직렬화·frame·batching과 protocol 호환성(version/capability, downgrade·unknown message 처리). [아키텍처 03](../../architecture/03_communication_protocol.md)이 `PRD-01-SP-02` 소유로 남긴 미결정 기술입니다.
- 마감 전 ACK 수신 시각을 다른 Peer가 검증하는 방법. `PRD-01-SP-03`의 미결정입니다. 이 값이 검증되지 않으면 6절의 한계 9가 마감을 우회하는 경로가 됩니다.
- [POL-02-R-08](../../policies/02_replication_consistency_retention.md)의 시계 차이 안전 차단. 그 규칙은 `PRD-01-SP-03`이 허용 오차를 확정하기 전까지 **참여 수락·주문 마감 수정·주문 상태 변경을 fail-closed로 막으라**고 요구하지만, 이 모델에는 그 게이트가 없습니다. 6절 한계 12입니다.
- 원작성자 결합과 event ID의 위·변조 방지 표현. `PRD-01-SP-04`의 미결정이며 6절의 한계 1이 여기에 걸립니다.

[PRD-01](../../prd/01_lunchtime_mvp.md) 9절이 정한 `PRD-01-SP-02`의 `실패 시 사용자 결과`는 "최신성·충돌을 확인할 수 없는 참여·메뉴는 **주문 완료와 요약 복사**를 막는다"입니다. 이 모델은 주문 완료 차단만 계산하고 요약 복사 경로를 만들지 않았습니다. 6절 한계 13입니다.

측정값을 추정으로 채우지 않은 [PRD-01-SP-01](./PRD-01-SP-01-peer-discovery.md)과 같은 원칙을 적용합니다. 이 스파이크는 **결정적 시뮬레이션에서 관측한 것만** 결론으로 씁니다. 실제 네트워크, 실제 시계, 실제 직렬화는 시험하지 않았고 그 범위는 6절에 남깁니다.

## 2. 모델 도구

`Experiments/SP02ReplicationModel`의 SwiftPM 패키지입니다. 앱 프로젝트와 분리된 독립 패키지이며 앱 번들에 실리지 않습니다.

[SP-01](./PRD-01-SP-01-peer-discovery.md)과 달리 이 도구는 **아무것도 측정하지 않습니다.** 검증 대상이 "같은 이벤트 집합이 같은 projection으로 수렴하는가"이므로, 실제 전송·시계·스케줄러에 의존하면 결론이 실행마다 달라져 증거가 되지 못합니다. 그래서 전송·시각·순서를 모두 시험이 직접 제어하는 결정적 시뮬레이션으로 만들었습니다.

### 구성

| 구성요소 | 책임 |
|---|---|
| `Ledger` | 수신 event의 멱등 append, 동일 ID·다른 payload 격리, 의존 record 부족 시 pending 보호와 승격, 권한·scope·revision·시간 검증 |
| `LedgerSummary` | 일일 세션·Room·데이터 종류 scope별 보유 범위 요약과 누락 계산 |
| `ProjectionReducer` | 검증 event 집합 하나를 구조화 운영 projection으로 접는 결정적 reducer |
| `LocalObservationProjection` | 네 안정 상태, never-shared 단독 Room 예외와 주문 전 점검 차단 사유 |
| `AntiEntropy` | 횟수·시간·record 예산 상한이 있는 대칭 대조 세션 |
| `FixtureCatalog` | 저장소에 고정한 결정적 시나리오 14개 |
| `sp02-replay` | fixture를 여러 도착 순서로 실행해 projection hash를 비교하는 실행 파일 |

### 두 종류의 projection을 분리한 이유

이 모델의 가장 중요한 구조 결정입니다. [아키텍처 04](../../architecture/04_replication_consistency_and_recovery.md)는 결정적 수렴 대상을 **구조화 운영 projection**으로 한정하고, 동기화 상태를 "로컬 StorageACK·session 관측을 입력으로 받는 로컬 관측 projection"으로 분리합니다.

모델도 그 경계를 타입으로 강제합니다.

- `StructuredProjection`은 검증된 장부만 입력으로 받습니다. 현재 시각, StorageACK 수신, Peer 접속 관측, pending·격리 상태가 들어가지 않습니다. **수렴 비교(hash)의 대상은 이것뿐입니다.**
- `LocalObservationProjection`은 위에 로컬 관측을 얹어 `이 기기에 저장됨`·`복제됨`·`동기화됨`·`확인 필요`와 주문 완료 차단 사유를 계산합니다. **같은 이벤트 집합을 가진 Peer 사이에서도 값이 다릅니다.**

이 경계를 지키지 않으면 정상 상태가 불일치로 보고됩니다. 4절 fixture 4가 그 사례입니다. 세 Peer의 구조화 projection이 완전히 같은데도 주문 완료 가능 여부는 셋 다 다릅니다.

### 결정성 장치

| 위험 | 이 모델이 쓰는 방식 |
|---|---|
| 실제 시계 | 모든 시각은 `Asia/Seoul` 자정 기준 분이며 fixture가 명시합니다. 코드 어디에서도 현재 시각을 읽지 않습니다 |
| 실제 전송 | fake transport가 도달 여부와 저장 회신 여부를 각각 제어합니다 |
| 무작위 순열 | splitmix64 생성기와 저장소에 고정한 Fisher-Yates 셔플을 씁니다. seed가 같으면 항상 같은 순열입니다 |
| 실행마다 달라지는 해시 | projection hash는 SHA-256입니다. `Hasher`처럼 실행마다 seed가 바뀌는 해시를 쓰면 두 실행을 비교할 수 없습니다 |
| 무한 반복 | 세션은 횟수·시간·record 예산 상한을 갖고 스스로 재시작하지 않습니다. 순열 수에도 상한이 있습니다 |

### 익명화

fixture와 출력에는 익명 라벨(`U1`, `D1`, `P1`, `R1`, `S1`)과 논리 시각만 씁니다. 메뉴 내용과 가게 이름은 projection에 **digest로만** 들어가고 원문은 보고서·출력 어디에도 나오지 않습니다. [POL-02-R-07](../../policies/02_replication_consistency_retention.md)이 진단에 "이벤트 ID, 상태 코드, 소요 시간과 익명화된 기기 식별자만" 허용하기 때문입니다.

출력의 `anonymized` 값은 선언이 아니라 **실제 검사 결과**입니다. fixture가 event에 실은 내용 원문을 event에서 직접 뽑아 직렬화한 전체 출력에서 찾고, 하나라도 남아 있으면 `false`가 됩니다. 상수로 선언하면 익명화가 깨진 순간에도 그대로 `true`이므로 그 값은 증거가 되지 못합니다.

## 3. 재현 절차

```bash
cd Experiments/SP02ReplicationModel
swift test
swift run sp02-replay --list
swift run sp02-replay --permutations 8
swift run sp02-replay --permutations 16 --seed 1
```

- `swift test`는 장부·projection·마감·로컬 관측·세션·보고서 계약의 회귀 테스트입니다.
- `sp02-replay`는 결과 JSON을 stdout으로, 진행 안내를 stderr로 냅니다. 리다이렉트로 원시 결과를 그대로 보관할 수 있습니다.
- `--permutations`는 서로 다른 도착 순서를 몇 개 시험할지 정합니다(2~64). **순열 0은 항상 fixture가 선언한 순서**이므로 선언 순서도 반드시 한 번 실행됩니다. 순서 의존을 **관측해야** 하는 fixture는 하한이 8로 올라갑니다 — 존재 명제를 무작위 순열의 우연에 맡기면 근거 없는 실패가 납니다.
- `--seed`가 같으면 항상 같은 순열이 나옵니다. 증거를 재현하려면 같은 값을 씁니다.
- 기대와 다른 fixture가 하나라도 있으면 종료 코드 `1`을 냅니다.

파일로 남길 때는 [SP-01](./PRD-01-SP-01-peer-discovery.md)과 같은 이유로 파일명에 UTC 시각을 넣습니다.

```bash
swift run sp02-replay --permutations 16 --seed 1 \
  > "sp02-replay-$(date -u +%Y%m%dT%H%M%SZ).json"
```

### 완료 조건별 근거

**1. 순서와 중복이 달라도 projection이 일치한다.**

fixture 1과 2가 같은 이벤트 집합을 각각 1회·3회 복사해 전달하고, 순열 8·16개로 도착 순서를 뒤섞습니다. 세 Peer 모두 `0b3e1a250044` 하나만 냈고 중복 전달은 hash를 바꾸지 않았습니다. `swift test`의 `같은 이벤트 집합은 도착 순서가 달라도 같은 projection hash를 만든다`는 무작위 없이 회전 순서와 역순으로 같은 결과를 고정합니다.

fixture 8은 여기에 분리·재결합을 더합니다. 분리 구간에는 두 Peer가 서로 다른 hash(`4bd43f506c7f`, `daeb55a16077`)를 냈고, 제한 세션 대조 한 번 뒤 둘 다 `0b3e1a250044`이 됐습니다. 이 값은 fixture 1의 hash와 같습니다 — 같은 event 집합에 도달하면 경로와 무관하게 같은 결과라는 뜻입니다.

**2. 전송 성공과 저장 ACK를 구분한다.**

fixture 4는 참여 record를 정상 전파한 뒤, 두 사람의 메뉴를 **상대 장부에는 도달시키되 저장 회신만 유실**시킵니다. 결과는 이렇습니다.

| Peer | 구조화 projection | 자기 메뉴 상태 | 주문 완료 |
|---|---|---|---|
| P1 (U1의 기기) | `0b3e1a250044` | `이 기기에 저장됨` | 차단 |
| P2 (U2의 기기) | `0b3e1a250044` | `이 기기에 저장됨` | 차단 |
| P3 (비참여 Peer) | `0b3e1a250044` | 남의 event만 보유 → `복제됨` | 가능 (7절 B에 달림) |

세 Peer의 구조화 projection은 완전히 같습니다. 메뉴가 실제로 상대 장부에 도달했기 때문입니다. **P3의 `가능` 판정은 7절 열린 결정 B에 직접 달려 있습니다** — 보유 자체를 `복제됨`의 근거로 세지 않기로 하면 이 칸은 `차단`이 됩니다. 그런데도 작성 기기는 자기 메뉴를 `복제됨`으로 올리지 않고 주문 완료를 막습니다. **전송 호출 성공이 저장 확인으로 승격되는 경로가 모델에 없다는 것**이 이 fixture의 결론입니다.

`swift test`의 `전송 호출 성공만으로는 복제됨이 되지 않는다`가 같은 계약을 단위 수준에서 고정하고, `정책 검증에 실패한 record는 StorageACK를 만들지 않는다`가 pending·rejected·격리에 ACK를 주지 않음을 확인합니다.

**3. 분기 메뉴와 다중 Room 참여에 자동 승자가 없다.**

fixture 6은 같은 사용자가 같은 parent에서 만든 리비전 두 개를 전파합니다. 세 Peer 모두 `diverged([E20,E21])`로 수렴하고 `메뉴 리비전 분기` 충돌과 주문 완료 차단을 계산했습니다. 회귀 테스트는 결과 값뿐 아니라 **`headEventID`가 `nil`임**을 함께 확인합니다. 나중 논리 순서나 마지막 쓰기를 몰래 고르는 경로가 없다는 뜻입니다. 사용자가 한쪽을 재확정하는 이벤트를 넣으면 분기가 해소되고 충돌이 사라집니다.

fixture 7은 분리 구간에 서로 다른 Room에서 확정된 같은 사용자의 참여 두 건을 만들고 재결합시킵니다. 세 Peer 모두 두 Room에서 `conflictedAcrossRooms`(정책 용어로는 [POL-02-R-05](../../policies/02_replication_consistency_retention.md)의 `참여 충돌`)로 수렴했고 양쪽 Room의 주문 완료가 막혔습니다. 사용자 선택 이벤트를 넣으면 유지할 Room만 확정으로 남고 나머지는 무효화됩니다. 선택 이벤트가 둘 이상이면 다시 `확인 필요`로 남습니다.

**4. 늦은 참여와 마감까지 ACK가 없던 참여가 다른 결과다.**

fixture 5는 마감 12:00을 기준으로 두 경로를 함께 돌립니다.

| 사용자 | 요청 | 수락 evidence | 요청 기기의 ACK 수신 | 결과 |
|---|---|---|---|---|
| U2 | 11:55 | 11:57 | 11:59 (마감 전) | `confirmed` — confirmation record가 **마감 뒤 단계에서 전파돼도** 유효 |
| U3 | 11:56 | 11:58 | 없음 | `failed(마감 전 승인 ACK 미수신)` |

U3가 마감 뒤(12:05)에 받은 ACK로 만든 confirmation record는 세 Peer 모두 `confirmationAfterDeadline`으로 거부했고(`rejectedEventCount: 1`), 소급 확정이 일어나지 않았습니다. 판정 근거는 **요청 기기가 ACK를 받은 시각**이며 전파 시각이 아닙니다.

**5. 결정적 보조 키와 완료 스냅샷.**

fixture 10은 논리 순서가 같은 `orderReverted(E43)`와 `orderCompleted(E44)`를 동시에 넣습니다. 세 Peer 모두 event ID 정렬로 `E44`를 마지막 유효 동작으로 계산했고, 두 이벤트를 반대 순서로 적용해도 결과가 같았습니다. 이어서 완료 스냅샷에 없던 유효 메뉴 리비전이 도착하자 완료가 `completedNeedsReview`로 내려가고 `완료 스냅샷과 현재 상태 불일치` 충돌이 붙었습니다. 완료 표식 자체는 장부에 남습니다.

### 독립 리뷰가 잡은 것

이 스파이크의 첫 candidate는 위 다섯 결론을 이미 내고 있었지만, 독립 리뷰가 **결론 자체를 무너뜨리는 결함 넷**을 찾았습니다. fixture 11·12·13과 그에 대응하는 회귀 테스트는 그 결과로 추가한 것입니다. 지금 통과하는 결과만 남기고 이 이력을 지우면, 다음 작업자가 같은 축을 다시 빠뜨립니다.

| 발견 | 무엇이 뚫렸는가 | 지금 상태 |
|---|---|---|
| 같은 Room에 두 번째 `roomCreated`가 무검증 통과하고, 마감 조회가 정렬 없는 사전 순회였다 | 같은 이벤트 집합이 **실행마다 다른 마감**을 적용했다. 마감을 14:20으로 늘려 잡은 위조 record를 끼우면 소급 확정 차단이 뚫렸다 | 정본 마감은 모든 생성 record의 **최소값**으로 fail-closed하고, 생성 record가 둘이면 `duplicateRoomRecord` 충돌([POL-02-R-03](../../policies/02_replication_consistency_retention.md)의 `확인 필요` 사유)로 남겨 주문 완료를 막는다. 이 최소값 판정의 소유자는 아래 네 번째 발견에서 장부가 아니라 projection으로 옮겼다. fixture 12와 `중복 생성 record에서 마감 판정이 도착 순서에 흔들리지 않는다` 테스트가 고정한다 |
| `orderCompleted`·`orderReverted`에 작성자 검증이 없었다 | 참여자도 생성자도 아닌 사용자가 남의 Room을 `주문 완료`로 만들 수 있었다 | 두 event가 메뉴와 같은 권한 record를 지목하도록 바꿨다. `POL-01-R-04` 권한 표의 "방 참여자 누구나"를 코드가 강제한다 |
| `roomCancelled`에 생성자 검증이 없었다 | 아무 Peer나 만든 tombstone에 **모든 Peer가 결정적으로 수렴**해 Room 전체가 복구 경로 없이 사라졌다 | 참조한 생성 record의 작성자일 때만 append하고, 정본 생성자와의 대조와 생성자 철회 뒤 취소는 projection에서 판정한다. 이 수정만으로는 부족했다 — 아래 세 번째 리뷰를 함께 읽어야 한다 |
| 격리한 envelope가 주문 전 점검에 아무 신호도 남기지 않았다 | 무결성 충돌이 사용자에게 보이지 않고 주문 완료가 그대로 통과했다 | 격리 envelope가 그 Room scope에 있으면 주문 완료를 막는다 |

같은 리뷰가 잡은 나머지: 남의 메뉴 head를 `supersedes`로 지목하는 리비전 통과, 같은 사용자가 기기만 바꿔 자기 요청을 수락하는 경로, 정책 거부된 event ID를 다른 payload로 재사용하는 경로, 그리고 출력의 `anonymized` 표시가 **실제 검사 없이 선언된 상수**였던 것.

이어진 정합성·테스트 관점 리뷰가 **완료 조건 자체를 깨는 결함 넷을 더** 찾았습니다.

| 발견 | 무엇이 뚫렸는가 | 지금 상태 |
|---|---|---|
| 마감 뒤에 작성한 confirmation이 수신 시각만 마감 전으로 신고하면 통과했고, 이미 기록된 `참여 실패`를 덮었다 | **완료 조건 4가 뚫렸다.** 4절이 fixture 5로 "충족"이라고 판정한 바로 그 게이트다 | confirmation 자신의 작성 시각도 마감 전이어야 하고, 같은 request에 실패 record가 있으면 실패가 종결이다. 두 도착 순서 모두에서 같은 결과임을 테스트가 고정한다 |
| 대조가 끝난 **뒤에** 로컬 append한 event가 `동기화됨`으로 읽혔다 | 상대가 가진 적 없는 메뉴로 주문 완료가 통과했다. **이 스파이크가 막으려는 메뉴 누락 그 자체다** | 대조 결과를 scope가 아니라 그 대조가 실제로 덮은 event 집합에 묶었다 |
| 생성자의 자동 참여가 중복 Room 참여 판정에서 빠졌다 | 같은 사람이 한 방은 생성자로, 다른 방은 확정 참여로 동시에 주문하는데 어느 쪽에도 `확인 필요`가 붙지 않았다 | `PRD-01-AC-01`대로 생성자 자동 참여도 참여로 세어 판정한다 |
| 충돌 집합 밖 confirmation을 지목한 선택이 사용자를 모든 방에서 조용히 제거했다 | 사용자가 아무 방에도 남지 않는데 `확인 필요`만 사라졌다 | 선택은 현재 충돌 집합 안의 confirmation을 골랐을 때만 적용한다 |

테스트 관점 리뷰는 뮤테이션 14건 중 **13건이 죽고 1건이 살아남는 것**을 보였습니다. 살아남은 것은 `AntiEntropy`의 "보류·거부·격리에는 ACK를 주지 않는다" 분기로, `swift test` 전체와 replay 전체에서 **실행 횟수 0**이었습니다. 기존 테스트가 발신 측에서 이미 거부된 record만 다뤄 애초에 전송 대상이 아니었기 때문입니다. 수신 측이 실제로 보류하는 전송을 만들어 그 분기를 실행하는 테스트를 넣었습니다. 보고서가 검증됐다고 적은 계약이 실제로는 한 번도 실행되지 않았다는 뜻이므로, 이 지적은 코드가 아니라 **증거의 공백**이었습니다.

같은 리뷰가 도구 자체의 결함도 찾았습니다. `same-id-payload-conflict`는 "순서 의존이 존재한다"는 **존재 명제**를 무작위 순열의 우연에 맡기고 있었습니다. 순열 2개에서는 seed 40개 중 18개가 근거 없이 실패했습니다(45%). 이슈의 `검증`이 "두 번 이상"을 요구하고 CLI가 `2~64`를 광고하므로, 리뷰어가 최소값으로 재현하면 절반 가까이 거짓 실패를 봅니다. 그런 fixture만 순열 하한을 8로 올려 판정을 우연에 맡기지 않게 했습니다. 그 밖에 테스트 두 곳이 `Dictionary` 순회로 도착 순서를 무작위화하던 것과, `daySessionConflicts` 배열 순서 때문에 `Equatable`과 `hash`가 다른 답을 낼 수 있던 것도 고쳤습니다.

세 번째 보안 관점 리뷰는 **위 권한 수정이 만든 새 공격면**을 찾았습니다.

| 발견 | 무엇이 뚫렸는가 | 지금 상태 |
|---|---|---|
| `roomCreated`는 여전히 무검증인데 동시에 취소·주문 상태의 **권한 근거**가 됐다 | 같은 Room ID로 자기 생성 record를 하나 심으면 그 record를 지목한 취소와 그 record를 근거로 한 주문 완료가 모두 장부를 통과했다. **event 하나를 더 심는 비용으로 두 번째 발견의 피해가 그대로 재현됐다** | 취소는 정본 생성자의 것만 적용하고, 생성 record가 둘 이상이면 취소를 적용하지 않으며 주문 완료를 확정으로 승격하지 않는다(불변식 17·18·32) |
| `roomCancelled`가 참조 record의 **종류**를 보지 않았다 | 심을 필요조차 없었다. 자기 참여 요청을 취소 대상으로 지목하면 작성자 검사가 그대로 통과했다. 그 Room에 자기 record를 하나라도 가진 사람은 누구나 방을 없앨 수 있었다 | 취소 대상이 `roomCreated`일 때만 append한다. 철회 tombstone에 이미 적용한 규칙(불변식 29)을 취소에도 적용한 것이다 |

**같은 원리를 다른 곳에도 적용해야 한다는 것이 그다음에 드러났습니다.** 위 수정을 리뷰에 넘기며 "장부에서 집합 전체를 조회하는 판정이 또 있는가"를 확인하다가, `참여 확정`의 마감 판정이 같은 결함을 갖고 있는 것을 찾았습니다. 리뷰어가 지적한 것이 아니라 이 질문을 준비하는 과정에서 나온 것입니다.

| 발견 | 무엇이 뚫렸는가 | 지금 상태 |
|---|---|---|
| 장부의 마감 조회가 **그 시점까지 도착한** 생성 record의 최소값을 썼다 | 마감을 줄여 잡은 두 번째 생성 record가 confirmation보다 **늦게** 온 Peer는 그것을 장부에 갖고 있고, 먼저 온 Peer는 거부했다. 같은 이벤트 집합에서 두 Peer의 **검증 장부 자체가 갈렸다.** 거부된 confirmation을 권한 record로 지목한 메뉴까지 한쪽에서만 보류돼, 완료 조건 1이 실제로 깨졌다 | 장부는 **요청이 선언한 생성 record**의 마감만 본다. 그 record는 선언된 의존이므로 값이 도착 순서에 흔들리지 않는다. 전체 집합의 최소 마감으로 다시 거르는 판정은 `ProjectionReducer`가 소유한다. fixture 14와 `마감을 줄여 잡은 생성 record는 도착 순서와 무관하게 같은 판정을 만든다` 테스트가 고정한다 |

fixture 12가 **늘려 잡은** 마감만 시험한 것이 이 결함을 가린 원인입니다. 반대 방향이 더 위험했습니다. 늘려 잡은 record는 최소값 판정에 지고, 줄여 잡은 record는 **이깁니다** — 이미 append된 event를 다시 판정하지 않는 append-only 장부에서는 "이긴다"가 곧 "먼저 본 Peer만 적용한다"가 됩니다.

`roomCreated`에 작성자 검증을 넣을 수는 없습니다. **누구나 방을 만들 수 있어야 하기 때문입니다.** 장부에서 "그 Room의 정본 생성 record인가"를 판정하려 해도, 그 답은 그 시점까지 도착한 event 집합에 의존하므로 같은 event가 Peer마다 다르게 판정돼 분기합니다. 그래서 이 방어선은 **전체 검증 집합을 보는 projection에** 두었습니다. 이 선택의 대가는 6절 한계 21입니다.

**첫 fixture 카탈로그가 이것들을 놓친 이유는 분명합니다.** 열 개 fixture 전부가 정직한 작성자만 등장시켰고 Room당 생성 record를 하나만 두었습니다. [테스트 표준](../../development/02_testing_standard.md)의 시나리오 축 가운데 `권한과 소유권`과 `보안과 신뢰 경계`를 통째로 빠뜨린 것입니다. 결정적 수렴을 확인하는 fixture만으로는 **권한 없는 쓰기가 결정적으로 수렴하는 상황**을 잡을 수 없습니다.

그 축을 채운 fixture 11도 처음에는 **남의 권한 record를 참조하는 경로만** 시험했습니다. `자기 record를 심어 권한을 스스로 발급하는` 경로는 그대로 비어 있었고, 그것이 세 번째 리뷰가 찾은 것입니다. fixture 13이 그 경로를 덮습니다.

마지막으로, 앞선 수정들이 만든 회귀 둘과 새 권한 구멍 하나를 더 고쳤습니다.

| 발견 | 무엇이 뚫렸는가 | 지금 상태 |
|---|---|---|
| 생성자 자동 참여를 중복 참여 **탐지**에만 넣고 **해소**에는 넣지 않았다 | 생성자 방에는 confirmation record가 없어 선택의 `kept`로도, `supersededByUserSelection`으로도 다뤄지지 않았다. 표현 가능한 유일한 선택을 넣으면 두 방이 모두 살아 있는데 `확인 필요`만 사라지고 **생성자 방이 다시 주문 완료 가능**해졌다 | 충돌 집합에 생성자 방이 있는 동안에는 어느 선택도 해소로 인정하지 않는다(불변식 27). 표현 자체가 불가능한 것은 한계 23이다 |
| `participationFailure`·`participationWithdrawal`이 작성자를 **사용자 ID로만** 검사했다 | 실패를 종결로 만든 수정과 겹쳐, 같은 사용자 ID를 주장하는 다른 기기가 record 하나로 확정 참여를 영구 실패로 뒤집었다. 실패를 해소하는 event가 없어 그 Room의 주문 완료가 **영구히** 막혔다 | 요청 기기·confirmation 작성 기기만 만들 수 있다(불변식 25). 이 결속이 있어야 한계 17을 "안전한 과잉 차단"으로 남길 수 있다 |
| 참여 상태가 없는 사용자의 메뉴가 projection에 들어갔다 | 심은 생성 record를 메뉴 권한으로 쓰면 `participants`에 없는 사람이 `menus`에 나타났다. 취소·완료는 막혔지만 **주문 요약 자체가 오염**됐다 | 참여 상태가 없는 작성자의 메뉴는 만들지 않는다(불변식 34) |

세 건 모두 **이전 수정이 만든 것**입니다. 앞의 둘은 한쪽 축만 고치고 대칭인 축을 두고 온 결과이고, 마지막은 권한 방어선을 취소와 주문 상태에만 적용한 결과입니다. 리뷰가 없었다면 셋 다 "고쳤다"는 기록만 남고 통과했을 것입니다.

그리고 **같은 패턴이 두 번 더 반복됐습니다.** 마지막 리뷰가 찾은 것입니다.

| 발견 | 무엇이 뚫렸는가 | 지금 상태 |
|---|---|---|
| 기기 결속을 수락·실패·철회에만 넣고 **중복 참여 선택과 메뉴 리비전**에는 넣지 않았다 | 같은 사용자 ID를 주장하는 다른 기기가 선택 event 하나로 **확정 참여자와 그 메뉴를 주문에서 제거**하고 `확인 필요` 차단까지 풀 수 있었다. 메뉴는 parent를 이어 붙여 head를 조용히 교체할 수 있었다. 둘 다 모든 Peer에 결정적으로 수렴한다 | 선택·메뉴·권한 record 모두 작성 기기를 요구한다(불변식 25). `POL-03-R-02`가 사용자 ID와 설치·기기를 1:1로 묶으므로 기기 불일치는 언제나 사칭이다 |
| 요약이 **event ID 집합만** 접었다 | 불변식 9가 projection에서 막은 구멍이 대조 계약에 그대로 남아 있었다. 두 Peer가 같은 ID의 서로 다른 payload를 하나씩만 보유하면 요약이 일치해 세션이 `수렴`으로 끝나고, **양쪽이 서로 다른 주문 요약을 들고 `동기화됨`·주문 가능**이 됐다. 격리는 두 payload를 모두 본 Peer에게만 생기므로 이 쌍을 잡지 못했다 | 요약에도 내용 digest를 접는다(불변식 35). 세션이 한도를 소진하고 양쪽이 `확인 필요`로 차단된다 |
| `roomRecordAmbiguous` 가드가 완료에만 있고 **되돌리기**에는 없었다 | 심은 생성 record를 권한 근거로 쓴 `orderReverted` 하나가 정당한 완료 표식을 모든 Peer에서 `진행 중`으로 지웠다 | 미확정 Room에서는 되돌리기를 확정 동작으로 보지 않고 마지막 완료를 `확인 필요`로 남긴다(불변식 32) |

**이 스파이크에서 리뷰가 찾은 결함은 한 종류로 수렴합니다 — "규칙을 세우고 그 규칙이 적용돼야 할 자리 중 일부를 빠뜨린 것".** 기기 결속, 정본 record 판정, 내용 digest, 미확정 Room 가드가 각각 처음 도입될 때는 한두 자리에만 들어갔고, 나머지 자리는 매번 다음 리뷰가 찾았습니다. 구현으로 옮길 때는 **불변식을 자리마다 손으로 적용하지 말고 참조·권한·요약을 한 곳에서 일괄 검사하는 형태**로 만들어야 합니다(한계 24).

## 5. 구현에 필요한 불변식

아래는 이 모델이 유지했기 때문에 결론이 성립한 조건입니다. 하나라도 깨면 위 결과가 재현되지 않습니다.

1. **이벤트는 불변이고 append-only다.** 수정·삭제는 새 revision 또는 tombstone이며 기존 payload를 제자리에서 덮지 않는다.
2. **이벤트가 자신의 의존 record ID를 선언한다.** 선언이 없으면 "의존 record 부족"과 "정책 위반"을 구분할 수 없고, 순서가 뒤집혀 도착한 정상 event가 폐기된다. 모델에서 참여 요청은 `roomCreated`를, 수락은 요청을, confirmation은 요청과 수락을, 메뉴는 parent·supersedes·권한 record를, 주문 완료는 스냅샷의 메뉴 head를 각각 의존으로 선언한다.
3. **pending/quarantine은 검증 장부와 분리된 저장 경계다.** 요약·StorageACK·projection·재전파의 입력으로 쓰지 않는다. 의존 record가 도착하면 **처음부터 다시 전체 검증**한 event만 승격한다.
4. **확정 참여는 세 record와 시각 조건을 모두 요구한다.** request, acceptor의 저장·정책 ACK evidence, requester의 confirmation record가 모두 있어야 하고 confirmation이 기록한 ACK 수신 시각이 마감보다 앞서야 한다. request와 acceptance만으로는 확정이 아니다. 이 시각 판정은 두 층에서 한다 — 장부는 **요청이 선언한 생성 record**의 마감으로, projection은 **정본(최소) 마감**으로 다시 본다. 이유는 불변식 33이다.
5. **수락 evidence는 요청 기기가 만들 수 없다.** 자기 요청을 자기 기기가 수락하면 `복제됨`의 "다른 피어" 조건이 무너진다.
6. **메뉴 event는 권한 record를 참조하고 본인만 만든다.** 권한 record는 자신의 confirmation 또는 never-shared 단독 Room에서 자신이 만든 `roomCreated`다. 참여 요청 record는 권한이 되지 않는다.
7. **메뉴 head는 "parent로 지목되지 않고 supersedes에 없는 리비전"이다.** head가 둘 이상이면 자동 선택을 금지하고 사용자 재확정 이벤트만 분기를 해소한다.
8. **projection은 (논리 순서, 이벤트 ID) 전순서만 사용한다.** 수신 시각과 도착 순서를 쓰면 Peer마다 다른 결과가 나온다.
9. **projection의 비교 표현과 Peer 사이 요약에 모두 내용 digest가 들어가야 한다.** 이벤트 ID와 리비전 번호만 담으면 같은 ID에 다른 메뉴 내용이 실린 envelope가 이겨도 비교 값이 같다. 이 결함은 실제로 이번 구현 중에 관측됐고 fixture 3이 그것을 잡았다. **이 digest는 Peer 사이 수렴 비교용이며 진단 로그나 외부 export 대상이 아니다.** 실제 메뉴명처럼 엔트로피가 낮은 원문은 digest만으로 사전 대입 복원이 가능하므로, 진단에 내보내야 한다면 [POL-02-R-07](../../policies/02_replication_consistency_retention.md)의 허용 범위 안에서 keyed digest 같은 별도 방식을 정해야 한다.
10. **14:30 쓰기 종료는 append 시점에 적용한다.** 마감 뒤 생성된 event는 어느 Peer에서도 장부에 들어가지 않는다.
11. **StorageACK는 append와 멱등 중복에서만 만든다.** pending, 정책 거부, 무결성 격리는 ACK 대상이 아니다.
12. **제한 세션은 횟수·시간·record 예산 상한을 갖고 스스로 재시작하지 않는다.** 한도를 소진하면 비교한 scope를 `동기화됨`에서 내리고 `확인 필요`로 남긴다.
13. **구조화 projection과 로컬 관측을 분리한다.** 동기화 상태, never-shared 단독 Room 예외, 주문 완료 가능 여부는 로컬 관측이며 수렴 비교 대상이 아니다. 이것을 섞으면 정상 상태가 불일치로 보고된다.
14. **주문 완료 이벤트는 점검에 사용한 참여자와 메뉴 head 스냅샷을 함께 기록한다.** 이 값이 없으면 늦게 도착한 유효 이벤트가 완료 조건을 깼는지 계산할 수 없다.
15. **강제 완료 경로를 만들지 않는다.** 차단 사유가 하나라도 있으면 완료할 수 없고 이를 우회하는 다른 진입점이 없다.
16. **주문 상태 이벤트도 권한 record를 지목한다.** 주문 완료·되돌리기는 작성자 자신의 confirmation 또는 자신이 만든 `roomCreated`를 참조해야 한다. 권한을 즉석 조회로 판정하면 순서가 뒤집혀 도착한 정상 event가 "권한 없음"으로 폐기된다. 불변식 6과 같은 분리를 따른다 — 장부는 권한 record의 존재와 소유만 보고, never-shared 조건과 참여 확정 여부는 로컬 관측이 fail-closed로 막는다(6절 한계 4·18).
17. **Room 취소는 정본 생성자만 만들고 대상은 생성 record여야 한다.** 대상 종류를 보지 않으면 그 Room에 자기 record를 하나라도 가진 사람이 자기 참여 요청을 지목하는 것만으로 방을 없앤다. 장부가 볼 수 있는 것은 **참조된 생성 record의 작성자**까지이므로, 정본 생성자와 대조하는 판정은 전체 검증 집합을 보는 projection이 소유한다. 생성자가 참여를 철회한 뒤의 취소도 적용하지 않는다. 이 세 가지 중 하나라도 빠지면 아무 Peer나 만든 tombstone에 모든 Peer가 결정적으로 수렴해 Room이 복구 경로 없이 사라진다.
18. **같은 Room의 생성 record가 둘 이상이면 Room 정보가 확정되지 않은 것으로 보고 fail-closed한다.** 정본 마감은 모든 생성 record의 최소값이고(이 판정은 projection이 소유한다 — 불변식 33), 그 Room을 `확인 필요`로 남기며, **취소를 적용하지 않고 주문 완료를 확정으로 승격하지 않는다.** 장부는 두 번째 record를 거부하지 않는다 — 어느 쪽이 남는지가 다시 도착 순서에 의존하기 때문이다. 정렬 없는 사전 순회로 "첫 일치"를 고르면 같은 입력이 실행마다 다른 마감을 적용한다. **장부·projection·로컬 관측의 모든 조회는 결정적 순서 위에서 수행해야 한다.**
19. **거부와 격리는 그 event ID를 비워 두지 않는다.** 거부한 payload digest를 기억하지 않으면 같은 ID에 다른 내용을 다시 실어 보내는 것만으로 검증을 통과시킬 수 있다.
20. **수락 evidence 검사는 기기와 사용자를 함께 본다.** 기기만 보면 같은 사용자 ID를 주장하는 두 번째 기기가 자기 참여를 스스로 확정한다.
21. **격리한 envelope는 그 scope의 주문 완료를 막는다.** 격리 대상이 참여 confirmation이나 메뉴 head가 아니어도 Room 정보나 주문 상태를 노린 것일 수 있다.
22. **`supersedes`도 소유권을 검사한다.** 버릴 분기 head가 본인·같은 Room의 메뉴여야 한다.
23. **익명화 표시는 선언이 아니라 검사 결과여야 한다.** 출력이 스스로를 익명이라고 주장하는 상수는 익명화가 깨진 순간에도 그대로 `true`다.
24. **confirmation은 수신 시각과 작성 시각이 모두 마감 전이어야 한다.** 수신 시각만 보면 마감 뒤에 만든 record가 "마감 전에 받았다"고 자기 신고하는 것만으로 통과한다. 작성 시각은 14:30 게이트가 이미 쓰는 값이므로 `PRD-01-SP-03`의 시계 결정과 무관하게 지금 검사할 수 있다.
25. **`참여 실패` outcome은 종결이고 실패·철회 record는 요청 기기만 만든다.** 같은 request에 실패 record가 있으면 뒤늦은 confirmation이 그것을 덮지 못한다. 둘이 함께 있는 것은 모순이므로 실패로 fail-closed한다. 종결이기 때문에 작성자 검사를 사용자 ID로만 하면 같은 ID를 주장하는 다른 기기가 확정 참여를 영구 실패로 뒤집고, 실패를 해소하는 event가 없어 그 Room의 주문 완료가 그대로 막힌다(6절 한계 17). 철회 tombstone과 중복 참여 선택도 같은 이유로 그 confirmation을 만든 기기만 만든다. 선택은 지목되지 않은 Room의 참여를 무효화하고 그 메뉴를 `revoked`로 만들며 그 사이 `확인 필요` 차단까지 없애므로, 철회와 같은 등급의 종결 효과다.
26. **대조 완료 표시는 scope가 아니라 그 대조가 실제로 덮은 event 집합에 묶는다.** scope만 기억하면 대조가 끝난 뒤 로컬 append한 event까지 `동기화됨`이 되고, 상대가 가진 적 없는 메뉴로 주문 완료가 통과한다.
27. **생성자의 자동 참여를 중복 참여 판정에 넣으면 해소 계약도 함께 정해야 한다.** 확정 참여만 세면 "한 방은 생성자로, 다른 방은 확정 참여로"가 탐지에서 빠진다. 그런데 탐지에만 넣으면 비대칭이 생긴다 — 생성자 방에는 confirmation record가 없어 선택의 `kept`로 지목될 수도, `supersededByUserSelection`으로 내려갈 수도 없다. 그 방을 그대로 두고 선택을 해소로 인정하면 두 방이 모두 살아 있는데 `확인 필요`만 사라지고 생성자 방이 다시 주문 가능해진다. 충돌 집합에 생성자 방이 있는 동안에는 어느 선택도 해소로 인정하지 않는다(6절 한계 23).
28. **중복 참여 선택은 현재 충돌 집합 안의 confirmation을 골라야 한다.** 집합 밖 record를 지목한 선택을 적용하면 사용자가 어느 방에도 남지 않는데 `확인 필요`만 사라진다.
29. **철회 tombstone도 대상 종류를 검증한다.** 검증하지 않으면 confirmation이 아닌 record를 지목한 tombstone이 철회 집합에 들어간다.
30. **취소된 Room도 마지막 유효 주문 동작을 계산한다.** 계산을 건너뛰면 완료 상태로 취소된 방이 `진행 중`으로 보인다.
31. **projection의 충돌 목록은 정렬해 반환한다.** 정렬하지 않으면 같은 event 집합에서 hash는 같은데 값 비교는 다른 답이 나온다.
32. **누구나 만들 수 있는 record를 권한 근거로 쓸 때는 그것이 정본인지 함께 본다.** `roomCreated`에는 작성자 검증을 넣을 수 없다 — 누구나 방을 만들 수 있어야 한다. 그런데 같은 record가 취소와 주문 상태의 권한 근거이므로, 같은 Room ID로 자기 생성 record를 심는 것만으로 그 Room의 쓰기 권한을 스스로 발급할 수 있다. **이 판정은 장부에서 할 수 없다.** "그 Room의 정본 생성 record인가"의 답은 그 시점까지 도착한 event 집합에 의존하므로, 같은 event가 Peer마다 다르게 판정돼 분기한다. 도착 순서와 무관한 전체 검증 집합을 보는 projection이 이 방어선을 소유해야 한다.
33. **장부 검증은 선언된 의존 record만 입력으로 쓴다.** 검증 집합 전체를 조회하는 판정은 그 시점까지 도착한 event에 의존하므로 같은 event가 Peer마다 다르게 판정된다. append-only 장부는 한 번 append한 event를 다시 판정하지 않으므로 **그 차이가 영구적**이고, 거부된 record를 의존으로 지목한 후속 event까지 한쪽에서만 보류돼 차이가 번진다. 집합 전체가 필요한 판정(정본 마감, 정본 생성 record, 중복 생성 record 여부)은 도착 순서와 무관한 projection이 소유해야 한다. 불변식 32는 이 규칙을 권한에 적용한 것이고, 불변식 4의 두 층 마감 판정은 시각에 적용한 것이다.
34. **projection은 참여 상태가 없는 사용자의 메뉴를 만들지 않는다.** 심은 생성 record를 권한 근거로 쓰면 참여자가 아닌 사용자의 메뉴가 수렴 projection에 들어간다. `participants`에 없는 사람이 `menus`에 있는 내부 불일치이고, 주문 요약에 낯선 메뉴가 그대로 표시된다. 참조 종류·권한 검사만으로는 막을 수 없다 — 그 메뉴 event 자체는 형식과 소유권을 모두 만족하기 때문이다.
35. **Peer 사이 요약도 보유 event의 내용 digest를 접는다.** event ID 집합만 접으면 불변식 9가 projection에서 막은 구멍이 **대조 계약에 그대로 남는다.** 두 Peer가 같은 ID의 서로 다른 payload를 하나씩만 보유하면 요약이 일치해 제한 세션이 `수렴`으로 끝나고, 양쪽이 서로 다른 주문 요약을 들고 `동기화됨`·주문 가능이 된다. 격리(불변식 21)는 한 Peer가 두 payload를 **모두** 본 경우에만 작동하므로 이 쌍을 잡지 못한다. 내용 digest를 접으면 요약이 불일치로 남아 세션이 한도를 소진하고 양쪽이 `확인 필요`로 차단된다.

## 6. 모델 한계

**추정으로 채우지 않고 확인하지 못한 것을 그대로 적습니다.**

1. **동일 ID·다른 payload는 도착 순서에 의존합니다.** [아키텍처 03](../../architecture/03_communication_protocol.md)의 수신 순서를 그대로 따라 "이미 보유한 payload를 유지하고 뒤에 온 것을 격리"하므로, 어느 payload가 장부에 남는지는 무엇이 먼저 왔는지에 달렸습니다. fixture 3의 P3가 순열 8개에서 서로 다른 hash 두 개를 냈습니다. **결정적 수렴은 이벤트 ID가 정직하게 발급된다는 전제 위에서만 성립합니다.** 그 전제를 세우는 원작성자 결합 표현은 `PRD-01-SP-04`의 미결정입니다.
2. **`복제됨` 판정은 보는 기기에 따라 다릅니다.** 남이 만든 event를 내가 보유하면 작성 기기와 나로 이미 복제본이 둘이므로 모델은 그것을 `복제됨`으로 계산합니다. 내가 만든 event는 남의 StorageACK가 있어야 합니다. [POL-02-R-03](../../policies/02_replication_consistency_retention.md)은 `복제됨`을 "최소 한 대의 다른 피어가 같은 최신 리비전을 저장했다고 ACK"로 정의하는데, **보유 자체를 그 조건으로 세는지는 명시하지 않습니다.** 7절의 열린 결정 B입니다.
3. **never-shared 단독 Room 예외는 로컬 관측이므로 수렴 대상이 아닙니다.** 발견·공유는 event를 만들지 않으므로 장부에서 계산할 수 없습니다. 모델은 발견 관측, 전송 이력, 참여 record, 원격 StorageACK 중 하나라도 있으면 예외를 즉시 없앱니다. 다만 `참여 record` 검사는 이름과 달리 **원격 record를 구조적으로 볼 수 없습니다** — 그 앞의 검사가 다른 기기의 event를 이미 걸러내므로 남는 것은 생성자 자신의 기기가 만든 record뿐입니다. 실제 효과는 "생성자가 자기 방에 참여 요청을 하나라도 남기면 예외가 사라진다"이며, 방향은 fail-closed지만 7절 C의 입력으로 쓸 때 이 차이를 알아야 합니다.
4. **예외가 사라진 뒤 생성자의 상태 전이는 정본에 없습니다.** 모델은 생성자의 자동 참여를 원격 confirmation이 없는 한 확정으로 보지 않고 주문 완료를 막습니다. 이미 만든 메뉴 event는 장부에 남깁니다. 이것은 [PRD-01](../../prd/01_lunchtime_mvp.md)과 [POL-02-R-04](../../policies/02_replication_consistency_retention.md)가 명시하지 않은 경계를 **fail-closed로 모델링한 것**이며 제품 확인이 필요합니다(7절 C).
5. **장부 요약을 이벤트 ID 집합의 digest로 모델링했습니다.** [아키텍처 03](../../architecture/03_communication_protocol.md)이 version vector·Merkle·set reconciliation을 미결정으로 남겼으므로 이 스파이크도 고르지 않았습니다. 모델이 고정한 것은 scope 분리와 누락 식별 가능성이라는 논리 계약뿐이고, **대규모 장부에서 요약을 비교·전송하는 비용은 답하지 않습니다.**
6. **논리 순서를 입력으로 받았습니다.** Lamport·HLC 등 clock 표현은 [아키텍처 04](../../architecture/04_replication_consistency_and_recovery.md)의 미결정입니다. 모델은 "모든 Peer가 공유하는 논리 순서와 이벤트 ID 보조 키"라는 계약만 고정하며, 그 논리 순서를 실제로 어떻게 발급하는지는 시험하지 않았습니다.
7. **fixture는 Peer 두세 대, 이벤트 열몇 건 규모입니다.** 순열도 최대 64개입니다. 실제 사내망 규모와 지연은 `PRD-01-SP-06`의 범위이며, 이 모델의 통과가 규모 안정성을 뜻하지 않습니다.
8. **채팅 lane과 재사용 히스토리 merge를 다루지 않았습니다.** 각각 `PRD-01-SP-05`와 별도 범위이며, 이 모델은 구조화 durable event만 대상으로 합니다.
9. **confirmation record의 ACK 수신 시각은 요청 기기의 자기 신고 값입니다.** 모델은 그 값을 그대로 신뢰합니다. 다른 Peer가 그것을 검증하는 방법은 `PRD-01-SP-03`의 미결정이며, **검증 없이 신뢰하면 마감 경계를 우회할 수 있습니다.** 7절 D입니다.
10. **저장 schema, pending/quarantine의 용량 한도와 eviction, outbound 복구 큐를 다루지 않았습니다.** 모델의 pending은 메모리에 무한히 남습니다. 실제 구현은 [POL-02-R-06](../../policies/02_replication_consistency_retention.md)의 최대 14일 창과 유한 용량 경계에 묶어야 합니다.
11. **취소·철회 tombstone의 만료 뒤 재등장은 시험하지 않았습니다.** 보존·GC 경계는 `PRD-01-SP-05`의 범위입니다.
12. **[POL-02-R-08](../../policies/02_replication_consistency_retention.md)의 시계 차이 안전 차단이 모델에 없습니다.** 그 규칙은 `PRD-01-SP-03`이 허용 오차를 확정하기 전까지 참여 수락, 주문 마감 수정과 주문 상태 변경을 fail-closed로 막으라고 요구합니다. 이 모델은 그 게이트 없이 append하므로, fixture 5의 `confirmed` 판정은 **POL-02-R-08이 현재 의존을 금지한 시계 체제를 전제**합니다. 한계 9와 함께 읽어야 합니다.
13. **주문 요약 복사 차단을 모델링하지 않았습니다.** [PRD-01](../../prd/01_lunchtime_mvp.md) 9절의 `실패 시 사용자 결과`는 주문 완료와 **요약 복사**를 함께 막으라고 정하는데, 이 모델에는 `canCompleteOrder`와 차단 사유만 있고 복사 경로가 없습니다. 구현은 같은 차단 사유 집합을 두 동작에 함께 적용해야 합니다.
14. **`AntiEntropy`의 거부·격리 ACK 분기는 도달 가능하지만 회귀 테스트가 없습니다.** 처음에는 "대조로 도달할 수 있는 것은 보류뿐"이라고 적었으나 독립 리뷰가 두 반례를 재현했습니다. 거부 분기는 발신 측이 유효로 본 record를 수신 측이 거부할 때 열리고(마감 판정이 장부에 있던 동안 실제로 그랬습니다 — 불변식 33), 격리 분기는 같은 ID를 **pending 또는 rejected**로 들고 있는 Peer가 그 ID를 요약에 갖고 있지 않아 전송 대상이 되면서 열립니다. `rejectedDigests`를 도입하며 생긴 경로인데 당시 이 문구가 따라오지 못했습니다. 회귀 테스트는 여전히 보류 경로만 실행합니다.
15. **마지막 참여자 철회가 Room 취소 전이를 만들지 않습니다.** [POL-01](../../policies/01_daily_room_lifecycle.md) 4.3은 "마지막 참여자의 철회도 같은 `모집 취소` 전이"를 요구하지만, 모델은 전원 철회 상태를 `withdrawn`으로만 두고 `cancelled`로 바꾸지 않습니다.
16. **중복 참여 충돌 중의 메뉴 쓰기를 장부에서 막지 않습니다.** [PRD-01-AC-11](../../prd/01_lunchtime_mvp.md)은 선택 전까지 "참여·메뉴 쓰기와 관련 방의 주문 완료"를 모두 막으라고 하는데, 모델은 완료 차단만 계산합니다.
17. **확정 실패한 참여자가 그 Room의 주문 완료를 영구 차단합니다.** 실패를 해소하는 event가 없어 방이 계속 막힙니다. 안전한 방향이지만 [POL-02-R-04](../../policies/02_replication_consistency_retention.md) 4.1의 "`참여 실패`로 처리하고 나머지는 진행"과 어긋납니다.
18. **불변식 6과 16은 코드가 강제하는 것보다 넓습니다.** 장부는 `roomCreated` 권한을 never-shared 조건과 무관하게 수락하고, 그 조건은 로컬 관측 계층에서만 봅니다. 주문 완료·되돌리기도 같은 분리를 따라, confirmation이 전혀 없는 생성자의 완료 event가 장부에 들어가고 차단은 `orderReadiness`만 담당합니다. 결과는 fail-closed지만 장부 진입 자체를 막지는 않습니다.
19. **Room 취소의 상태 조건 일부를 검사하지 않습니다.** [POL-01-R-04](../../policies/01_daily_room_lifecycle.md)는 전체 취소를 "현재 참여 중인 방 생성자, 주문 진행 중"으로 한정합니다. 모델은 생성자 여부와 철회 여부까지만 보고 **주문 상태가 `주문 완료`일 때 취소를 막지 않습니다.** 이때 붙는 `완료 스냅샷과 현재 상태 불일치` 충돌은 스냅샷이 실제로 깨져서가 아니라 취소가 참여자를 전원 `withdrawn`으로 만든 부수 효과입니다. 사용자에게 보일 사유 문구가 실제 원인과 다릅니다.
20. **격리에는 해소 경로가 없습니다.** `Ledger.quarantined`를 비우는 동작이 없으므로, 자동 신뢰 Peer 하나가 그 Room의 아무 event ID에 다른 payload를 **한 번** 실어 보내면 불변식 21이 그 Peer의 주문 완료를 그날 내내 막습니다. 방향은 fail-closed로 옳지만, 이는 곧 **임의 Peer가 주문 완료를 영구 차단할 수 있다**는 뜻이기도 합니다. 정상 event를 전부 다시 받아도 격리 수는 줄지 않습니다. 복구 계약은 7절 A입니다. **차단 범위는 그 Room보다 넓어질 수 있습니다** — 대상이 일일 세션 scope(`room == nil`) event면 그날의 **모든 Room**이 막힙니다.
21. **불변식 17·18·32·33의 방어선이 projection 계층에만 있습니다.** 심은 생성 record는 장부에 남고 지워지지 않으므로, 취소와 확정 완료를 막는 대신 그 Room이 그날 내내 `duplicateRoomRecord` 충돌로 `확인 필요`에 머뭅니다. **아무 Peer나 event 하나로 Room 하나의 주문 완료를 영구 차단할 수 있다**는 점에서 한계 20과 같은 종류이며, 복구 경로도 마찬가지로 없습니다. 또한 이 방어선을 장부에 둘 수 없으므로(불변식 32), **구조화 projection을 거치지 않고 장부를 직접 읽는 경로를 만들면 같은 보호를 받지 못합니다.** 차단 방향은 승격에만 있는 것이 아닙니다 — **이미 `완료`로 확정된 주문도 record 하나로 `확인 필요`로 끌어내릴 수 있고**, 남의 never-shared 단독 Room 예외도 record 하나로 영구히 파괴할 수 있습니다(그 Room은 원격 ACK를 받을 방법이 없으므로 그날 내내 주문이 막힙니다). 근본 해소는 원작성자 결합(한계 1, `PRD-01-SP-04`)이 생성 record의 위조를 막을 때 가능합니다.
22. **장부는 마감을 늘려 잡은 생성 record를 지목한 참여 요청을 통과시킵니다.** 불변식 33에 따라 장부는 선언된 record의 마감만 보므로, 위조 record를 지목한 요청의 confirmation은 장부에 남습니다. 확정으로 승격되지 않는 것은 정본 마감으로 다시 거르는 projection 덕분입니다. 방향은 fail-closed지만, 한계 21과 같은 이유로 **장부만 읽는 경로는 그 confirmation을 유효한 것으로 볼 수 있습니다.** `마감을 늘려 잡은 생성 record를 지목한 요청은 확정으로 승격되지 않는다` 테스트가 이 경계를 그대로 고정합니다.

23. **생성자 방을 유지하겠다는 선택을 모델이 표현할 수 없습니다.** `duplicateParticipationSelection`의 `kept`는 confirmation record여야 하는데 생성자 자동 참여 방에는 그 record가 없습니다. 그래서 "내가 만든 방을 유지하고 남의 방 참여를 버린다"를 말할 방법이 없고, 불변식 27에 따라 그 충돌은 계속 `확인 필요`로 남습니다. [PRD-01-AC-11](../../prd/01_lunchtime_mvp.md)이 "사용자가 유지할 방을 직접 선택"을 요구하므로 이 해소 경로는 제품 계약에 필요합니다. 생성자에게 남은 다른 탈출구인 `roomCancelled`도 해소하지 못합니다 — 중복 참여 판정이 취소 적용보다 **먼저** 실행되므로, 생성자 방을 취소해도 그 방은 `withdrawn`이 되는데 일일 세션 충돌은 여전히 그 사용자를 두 방 중복으로 셉니다. 살아 있는 참여가 하나뿐인데 `conflictedAcrossRooms`가 남는 자기 모순이고, 그 차단이 **상대 Room의 무관한 참여자에게까지** 미쳐 그 사람들도 그날 내내 주문을 완료하지 못합니다. 선택 record가 방을 지목하게 할지, 생성자 참여에도 확정 record를 만들지는 이 스파이크가 정할 수 없습니다.
24. **참조 record 종류 검사가 아직 모든 필드에 있지 않습니다.** 이번 작업에서 참여 요청·수락·실패·철회·취소의 대상 종류를 검사하게 했지만, `orderCompleted`·`orderReverted`의 `roomRecord`는 여전히 종류를 보지 않습니다. 그 필드는 권한 근거가 아니고(권한은 별도 `authority`) reducer도 값을 쓰지 않아 현재 영향이 없습니다. 다만 "어떤 참조가 종류를 선언하고 검사받는가"가 EventKind마다 흩어져 있어, 새 EventKind를 추가할 때 같은 구멍이 다시 생깁니다. `orderCompleted`의 `snapshot.menuHeads`는 더 넓게 비어 있습니다 — 의존으로만 선언되고 종류·소유·scope 어느 것도 검사받지 않습니다(reducer가 실제 상태와 대조해 `completedNeedsReview`로 fail-closed하므로 현재는 무해합니다). 모든 참조가 기대 종류를 선언하고 검증이 일괄 검사하는 형태가 필요합니다.
25. **`same-id-payload-conflict`의 순열 하한이 flake를 없애지 못했습니다.** 하한을 8로 올려 seed 40개 중 18개 실패를 0으로 만들었지만, seed 1000개 전수에서는 4개(0.4%)가 여전히 종료 코드 1을 냅니다. "순서 의존이 존재한다"는 존재 명제를 무작위 순열에 맡기는 구조가 그대로이기 때문입니다. 드문 flake는 잦은 실패보다 진단이 어렵습니다. hash가 달라야 하는 **명시적 도착 순서 쌍**을 fixture가 witness로 선언해 항상 실행하는 형태로 바꿔야 합니다.
26. **존재하지 않는 의존 record를 선언한 event 하나가 그날 세션 전체를 막습니다.** 그 event는 영구 pending으로 남고 불변식 3에 따라 요약·재전파에서 빠지므로 다른 Peer가 채워 줄 수도 없습니다. 주문 전 점검은 pending이 있으면 차단하는데(`pendingDependencyUnresolved`) 그 검사가 `room == nil`인 event를 모든 Room에 적용하므로, 일일 세션 scope의 event 하나로 그날의 **모든 Room**이 막힙니다. 한계 10은 pending을 저장 용량 문제로만 다뤘고 이 차단 표면은 적지 않았습니다. 복구 계약은 7절 A·F와 함께 정해야 합니다.

## 7. 제품 결정이 필요한 열린 항목

아래는 이 스파이크가 답할 수 없고 Product Owner 결정이 필요한 항목입니다.

**모델의 기본값이 모두 fail-closed인 것은 아닙니다.** A·C·E·F는 차단 쪽으로, **B와 D는 허용 쪽으로** 두었습니다. [PRD-01](../../prd/01_lunchtime_mvp.md) 9절이 `실패 시 사용자 결과`를 "확정 전에도 적용하는 실패 시 안전 차단(fail-closed) 결과"로 정의하므로, B와 D는 그 기본값을 아직 만족하지 못한 상태입니다. 각각 6절 한계 2와 9에 대응합니다.

**A와 F는 차단 쪽이지만 그 자체로 문제가 있습니다.** 둘 다 해소 경로가 없어, 아무 Peer나 event 하나로 그 Room의 주문 완료를 **그날 내내 차단**할 수 있습니다(6절 한계 20·21). 차단 방향이 옳다는 것과 복구 경로가 없어도 된다는 것은 다른 이야기입니다.

| # | 열린 결정 | 모델의 현재 동작 | 결정이 필요한 이유 |
|---|---|---|---|
| A | 동일 ID·다른 payload를 만난 Peer에게 무엇을 보여줄 것인가 | 격리한 envelope의 scope에 걸린 Room의 주문 완료를 막고 해당 event를 `확인 필요`로 내린다. 어느 payload가 장부에 남는지는 도착 순서에 달렸다(6절 한계 1) | 정본은 "격리한다"까지만 정한다. 사용자에게 어떤 복구 경로를 줄지와 격리가 그 Room의 다른 데이터까지 무효화하는지가 없다. 해소 경로가 없으면 임의 Peer가 주문 완료를 영구 차단할 수 있다(6절 한계 20) |
| B | 남이 만든 event를 내가 보유한 사실을 `복제됨`의 근거로 셀 것인가 | **센다(fail-open)** | [POL-02-R-03](../../policies/02_replication_consistency_retention.md)이 명시하지 않는다. 세지 않으면 비작성 Peer의 표시가 달라지고, 세면 "ACK"의 의미가 넓어진다 |
| C | never-shared 예외가 사라진 뒤 생성자의 참여·메뉴를 어떻게 둘 것인가 | 참여를 `확인 필요`로 내리고 기존 메뉴 event는 장부에 남긴다 | [POL-02-R-04](../../policies/02_replication_consistency_retention.md)는 "다른 피어와 공유·발견되거나 원격 이력이 생기면 이 예외는 즉시 사라진다"까지만 정한다. 이미 만든 데이터의 처리가 없다 |
| D | 마감 전 ACK 수신 시각을 다른 Peer가 어떻게 검증할 것인가 | **자기 신고 값을 신뢰한다(fail-open)** | 검증 없이 신뢰하면 마감을 우회할 수 있다. `PRD-01-SP-03`의 허용 오차·검증 방식과 함께 결정해야 한다 |
| E | 중복 참여 선택 이벤트가 둘 이상일 때 | 어느 쪽도 채택하지 않고 `확인 필요`를 유지한다 | [POL-02-R-05](../../policies/02_replication_consistency_retention.md)는 선택이 하나인 경우만 규정한다 |
| F | 같은 Room에 생성 record가 둘 이상일 때 무엇을 보여주고 어떻게 되돌릴 것인가 | 결정적 첫 record를 Room 정보로 쓰고 마감은 최소값으로 fail-closed하며, 취소를 적용하지 않고 주문 완료를 확정으로 승격하지 않는다. 그 Room은 그날 내내 `확인 필요`에 머문다(6절 한계 21) | 정본에 중복 생성 record 개념이 없다. 어느 record를 정본으로 볼지, 사용자가 어떻게 해소할지, 그리고 그 사이 참여자들이 주문을 진행할 수 있는지가 정해지지 않았다 |

## 8. 문서 영향

이 스파이크는 **사용자에게 보이는 계약을 바꾸지 않습니다.** 모델은 [PRD-01](../../prd/01_lunchtime_mvp.md), [POL-02](../../policies/02_replication_consistency_retention.md)와 [아키텍처 03·04](../../architecture/README.md)의 기존 규칙을 실행 가능한 형태로 옮겨 확인했고, 새 규칙을 만들지 않았습니다. 그래서 이번 변경에서 PRD와 Policy를 갱신하지 않았습니다.

다만 아래 세 가지는 **후속 작업으로 남습니다.** 이 이슈의 변경 허용 경로가 `Experiments/SP02ReplicationModel/**`과 이 문서뿐이므로 여기서 처리할 수 없습니다.

- 7절의 열린 결정 A~F와 6절 한계 12~26을 [결정 목록](../../product-definition/10_decision_backlog.md)에 미결정 항목으로 옮겨야 합니다. 그 파일을 소유한 별도 작업이 필요합니다. 그때까지는 이 문서 7절이 열린 결정 A~F의, 6절이 한계 12~26의 기록입니다.
- 열린 결정이 확정되면 [PRD-01](../../prd/01_lunchtime_mvp.md) 또는 [POL-02](../../policies/02_replication_consistency_retention.md)를 갱신하고 새 결정 ID를 연결해야 합니다.
- [아키텍처 03](../../architecture/03_communication_protocol.md)과 [04](../../architecture/04_replication_consistency_and_recovery.md)의 `미결정 기술` 표에서 `PRD-01-SP-02`가 소유한 항목(wire schema, protocol 호환성, 요약·누락 request 형식, StorageACK correlation, 참여 확정 record 표현, 충돌 구현, 논리 순서)은 이 모델이 논리 계약만 고정했을 뿐 확정 기술을 고르지 않았으므로 **그대로 유지됩니다.** 5절의 불변식을 그 표에 반영하는 변경은 해당 파일을 소유한 별도 작업에서 수행해야 합니다.
